맥에서 WordPress 이미지 용량 줄이기: 리사이즈·WebP 변환 워크플로

원본 보관부터 리사이즈, WebP·AVIF 비교, WordPress 업로드 후 확인까지 유료 플러그인 없이 반복해서 사용할 수 있는 이미지 최적화 과정을 정리했습니다.

맥 워크플로 NOTE 024

Written by

WordPress는 이미지를 올릴 때 여러 크기를 만들고 브라우저가 화면에 맞는 파일을 고르도록 도와줍니다. 그렇다고 카메라 원본이나 4K 스크린샷을 그대로 올려도 된다는 뜻은 아닙니다. 업로드 전에 실제 표시 크기로 줄이고 콘텐츠에 맞는 포맷을 고르면 유료 최적화 플러그인 없이도 전송량을 크게 줄일 수 있습니다.

이 글은 M1 Pro Mac과 WordPress 7.0.2 환경에서 확인한 결과를 바탕으로, 원본 보관 → 리사이즈 → 포맷 변환 → WordPress 확인을 반복 가능한 작업으로 정리합니다.

1. 원본과 업로드본을 먼저 분리한다

이미지 폴더를 original, convert, upload-ready 세 단계로 나눕니다. 원본은 건드리지 않고 복사본만 변환합니다. 그래야 압축 품질이 나쁘거나 잘못 잘랐을 때 다시 시작할 수 있고, WordPress 미디어 파일을 원본 보관소처럼 사용하는 실수도 피할 수 있습니다.

2. WordPress가 해주는 일과 못 해주는 일을 구분한다

WordPress는 업로드한 이미지에서 여러 중간 크기를 만들고, 생성한 HTML에 srcset과 sizes를 추가합니다. 브라우저는 이 정보를 보고 화면 폭과 해상도에 적합한 파일을 선택할 수 있습니다. 자세한 동작은 WordPress 반응형 이미지 공식 문서에서 확인할 수 있습니다.

WordPress는 기본적으로 PNG를 제외한 이미지의 한 변이 2,560px를 넘으면 축소본을 만들어 가장 큰 사용 이미지로 삼고 원본도 보관합니다. 다만 테마의 실제 표시 크기, 콘텐츠에 맞는 포맷, 시각 품질까지 판단하지는 않습니다. 본문에서 최대 1,200px로 표시할 사진이라면 6,000px 원본을 업로드 전에 적정 크기로 줄이는 편이 저장 공간과 백업 시간까지 아낍니다. 자세한 기본 동작은 WordPress 대형 이미지 공식 안내에서 확인할 수 있습니다.

3. 이미지 종류에 따라 포맷을 고른다

  • 사진: JPEG, WebP, AVIF를 같은 화면 크기로 비교합니다.
  • 작은 글자가 있는 UI 스크린샷: PNG와 WebP를 100% 확대해 글자 번짐을 확인합니다.
  • 투명 배경 이미지: 알파 채널이 필요한지 확인하고 WebP 또는 PNG를 비교합니다.
  • 로고와 단순 도형: 출처가 안전한 벡터 원본이 있다면 SVG가 적합할 수 있지만, WordPress 업로드 정책과 보안 설정을 먼저 확인합니다.

‘가장 최신 포맷’이 매번 가장 작은 것은 아닙니다. 같은 품질 숫자도 포맷 사이에서 같은 시각 품질을 뜻하지 않으므로 파일 크기와 실제 화면을 함께 봐야 합니다.

4. 한두 장은 Finder 빠른 동작으로 처리한다

Finder에서 이미지를 선택하고 빠른 동작 → 이미지 변환을 사용하면 별도 앱 없이 크기와 포맷을 바꿀 수 있습니다. Apple의 Finder 빠른 동작 안내는 HEIC 사진을 JPEG나 PNG로 바꾸는 예를 제공합니다. 현재 Mac의 지원 포맷은 파일 종류와 확장 기능에 따라 달라질 수 있으므로 WebP가 기본으로 된다고 단정하지 않습니다.

5. 반복 변환은 cwebp 명령으로 고정한다

WebP 변환을 반복한다면 Google의 cwebp 도구를 사용해 규칙을 명령으로 남길 수 있습니다. Homebrew의 WebP formula로 설치한 뒤, 가로 사진은 너비를 1,600px로, 세로 사진은 높이를 1,600px로 지정할 수 있습니다. 품질은 82로 설정하고 메타데이터는 복사하지 않는 예시입니다.

brew install webp

# 가로 사진: 너비 1,600px, 높이는 비율에 맞춰 계산
cwebp -preset photo -q 82 -resize 1600 0 -metadata none input.jpg -o output.webp

# 세로 사진: 높이 1,600px, 너비는 비율에 맞춰 계산
cwebp -preset photo -q 82 -resize 0 1600 -metadata none input.jpg -o output.webp

-q는 0부터 100 사이의 손실 압축 품질, -resize는 크기 변경, -metadata none은 메타데이터 제거 옵션입니다. -resize 1600 0은 긴 변을 자동으로 찾는 명령이 아니라 너비를 지정하는 명령입니다. 따라서 먼저 이미지 방향과 크기를 확인하고, 이미 1,600px보다 작은 파일은 확대하지 않도록 변환 대상에서 제외합니다. 투명 이미지나 글자가 많은 화면에는 같은 값을 그대로 적용하지 말고 cwebp 공식 옵션의 -lossless, -preset text 등을 별도로 시험합니다.

6. 실제 Odd Note 이미지로 비교해 봤다

2026년 8월 18일, 이 사이트의 1,200×630 공유 카드 PNG를 WordPress의 Imagick 편집기로 변환했습니다. 원본은 992,289바이트였고 JPEG·WebP·AVIF는 모두 품질 82로 저장했습니다.

이 한 장에서는 WebP가 AVIF보다 작았습니다. 다만 같은 품질 숫자가 동일한 시각 품질을 보장하지 않으므로 이 표만으로 포맷의 우열을 정할 수는 없습니다. 실제 글에 쓸 사진과 글자가 있는 스크린샷을 각각 변환해 모바일 화면과 100% 확대 상태에서 확인해야 합니다.

7. AVIF는 서버 지원부터 확인한다

WordPress는 6.5부터 AVIF 업로드를 지원하지만 서버의 GD 또는 Imagick 라이브러리가 AVIF를 처리할 수 있어야 합니다. 관리자 화면의 도구 → 사이트 건강 → 정보 → 미디어 처리에서 지원 포맷을 확인합니다. 이 Odd Note 서버는 점검 당시 Imagick을 사용했고 WebP와 AVIF를 모두 지원했습니다. 환경별 차이는 WordPress AVIF 공식 안내를 참고합니다.

8. 업로드 후 네 가지를 다시 본다

  1. 미디어 정보에 기대한 픽셀 크기와 포맷이 표시되는가?
  2. 본문 HTML에 적절한 srcset과 sizes가 생성됐는가?
  3. 첫 화면에서 가장 큰 대표 이미지를 불필요하게 지연 로딩하지 않았는가?
  4. 모바일 네트워크에서 실제 전송 파일이 원본보다 작은가?

최적화 플러그인을 추가했다면 같은 이미지를 두 번 압축하지 않는지도 확인합니다. 파일 크기 감소는 로딩 경험을 개선할 수 있지만 검색 순위나 PageSpeed 점수 상승을 보장하지는 않습니다.

발행 전 이미지 체크리스트

  • 원본과 업로드본을 다른 폴더에 보관했다.
  • 실제 표시 크기보다 지나치게 큰 파일을 줄였다.
  • 사진과 스크린샷을 서로 다른 기준으로 비교했다.
  • 파일명과 대체 텍스트가 이미지 내용을 설명한다.
  • WebP·AVIF 서버 지원을 사이트 건강에서 확인했다.
  • 모바일과 100% 확대 화면에서 품질을 확인했다.
  • 변환 전후 크기와 작업 규칙을 기록했다.

결론: 이미지 최적화는 포맷 하나를 고르는 일이 아니라, 실제 표시 크기·콘텐츠별 품질·WordPress 반응형 이미지·측정을 하나의 반복 가능한 Mac 워크플로로 묶는 일입니다.
