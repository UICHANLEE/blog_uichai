2026년 6월 11일, Supabase는 Realtime Broadcast에서 바이너리 payload를 주고받을 수 있다고 발표했습니다. 그동안 주로 JSON 객체를 보내던 채널에 이제 ArrayBuffer, Uint8Array, 데이터베이스의 bytea 같은 이진 데이터를 그대로 실을 수 있게 된 것입니다.

센서 수치, 위치 좌표, 오디오 조각, JPEG·PNG 프레임처럼 본래 바이너리인 데이터를 다루는 개발자에게는 반가운 변화입니다. JSON 문자열이나 Base64로 바꾸었다가 다시 복원하는 과정을 줄일 수 있기 때문입니다. WebSocket 클라이언트뿐 아니라 REST API와 데이터베이스 함수에서도 바이너리 Broadcast를 보낼 수 있습니다.

하지만 여기서 “이제 실시간 앱의 신뢰성 문제도 해결됐다”고 결론 내리면 중요한 부분을 놓칩니다. 바이너리는 메시지를 효율적으로 운반하는 형식이지, 메시지가 반드시 도착하도록 보장하는 장치가 아닙니다.

실시간 앱의 어려움은 메시지를 빨리 보내는 데 있지 않았다. 누군가 메시지를 놓쳐도 결국 모든 화면이 같은 상태에 도달하도록 만드는 데 있었다.

6월 11일 발표에서 실제로 달라진 것

여기까지는 Supabase 공식 발표로 확인된 사실입니다. JavaScript에서는 ArrayBuffer나 ArrayBufferView를 WebSocket으로 보낼 수 있고, REST API에서는 Content-Type: application/octet-stream을 사용합니다. 데이터베이스에서는 realtime.send_binary() 함수에 bytea 값을 전달할 수 있습니다.

활용처도 비교적 분명합니다. 온도·가속도·GPS 같은 수치를 반복해서 보내는 센서 스트림, 화면 캡처나 프레젠테이션 프레임을 실시간으로 공유하는 기능, 숫자가 촘촘하게 들어간 시계열처럼 JSON의 텍스트 표현이 부담이 되는 상황입니다. 필드 이름과 구분 기호를 반복하는 대신 송신자와 수신자가 합의한 형식으로 값을 고정 길이 바이트에 담을 수 있습니다.

지원 버전은 반드시 확인해야 합니다. 2026년 8월 19일 기준 공식 변경 기록은 WebSocket 바이너리 지원에 supabase-js 2.91.0 이상 또는 supabase-swift 2.44.0 이상을 요구합니다. JavaScript의 REST httpSend는 supabase-js 2.107.0 이상이 필요합니다. 지원하지 않는 구버전 SDK에서는 바이너리 메시지가 명확한 오류 없이 조용히 버려질 수 있다고 경고합니다.

앱 버전이 여러 개 공존하는 서비스라면 곧바로 전환하기보다 클라이언트가 바이너리를 받을 수 있는지 확인하는 capability handshake나 기능 플래그가 필요합니다. 혼합 환경에서는 JSON fallback을 잠시 유지하는 편이 안전합니다.

모든 payload를 바이너리로 바꿀 필요는 없다

여기부터는 공식 기능을 바탕으로 한 설계 판단입니다. 화면 모드가 waiting에서 live로 바뀌었다는 작은 이벤트는 JSON으로 보내도 충분히 작고 로그에서 읽기도 쉽습니다. 반대로 초당 여러 차례 발생하는 센서 값이나 이미지 프레임은 바이너리의 이점이 커집니다.

바이너리는 크기를 줄이는 대신 사람이 바로 읽기 어려운 protocol을 만듭니다. 첫 바이트는 메시지 종류, 다음 바이트는 protocol 버전, 이어지는 값은 sequence와 실제 payload라는 식의 계약이 필요합니다. 송신자와 수신자의 버전이 어긋나면 JSON보다 조용하고 복잡한 오류가 생길 수 있습니다. 따라서 “쓸 수 있는가?”보다 전송 빈도와 크기가 protocol 복잡성을 감수할 만큼 큰가?를 먼저 물어야 합니다.

한도도 함께 봐야 합니다. 2026년 8월 19일 Realtime Limits 문서의 기본값은 Free 요금제에서 동시 연결 200개, 초당 메시지 100개, Broadcast payload 256KB입니다. Pro는 각각 500개, 500개, 3,000KB입니다. 한도는 요금제와 프로젝트 설정에 따라 바뀔 수 있으므로 실제 배포 전 최신 문서를 다시 확인해야 합니다.

큰 이미지나 영상을 보관해야 한다면 Broadcast에 계속 밀어 넣기보다 객체 저장소에 올린 뒤 작은 식별자나 URL만 알리는 편이 낫습니다. 바이너리 지원은 Realtime을 범용 파일 전송 서비스로 바꾼 것이 아닙니다.

여러 화면을 동시에 바꾸는 앱에서 배운 것

여러 모바일 화면을 한 관리 신호에 맞춰 전환하는 웹 앱을 설계한 적이 있습니다. 사용자는 각자의 휴대폰으로 접속하고, 관리자가 상태를 바꾸면 모든 화면이 가능한 한 빠르게 같은 모드로 이동해야 했습니다. 조직명과 행사 정보는 공개하지 않고, 여기서는 재사용할 수 있는 아키텍처만 설명합니다.

처음 떠올리기 쉬운 방법은 간단합니다. 관리자가 버튼을 누르면 WebSocket 채널에 mode_changed 이벤트를 보내고, 모든 클라이언트가 이벤트를 받아 화면을 바꾸는 것입니다. 연결이 유지되는 동안은 빠르고 코드도 짧습니다.

문제는 실제 휴대폰이 이상적인 WebSocket 클라이언트처럼 행동하지 않는다는 점입니다. 화면을 잠갔다가 돌아올 수 있고, 와이파이와 이동통신망 사이를 오갈 수 있으며, 브라우저가 백그라운드 탭의 실행을 늦출 수도 있습니다. 연결이 끊긴 순간에 상태 변경 이벤트가 지나가면 그 기기만 이전 화면에 머물 수 있습니다.

서버리스 함수의 프로세스 메모리도 모든 요청이 공유하는 영속 상태처럼 취급할 수 없습니다. 그래서 최종 구조는 WebSocket을 저장소가 아니라 변경을 빠르게 알리는 신호선으로 취급했습니다.

1. Redis를 상태의 원본으로 둔다

관리자가 화면 모드를 변경하면 먼저 Redis에 최종 상태를 기록합니다. 상태에는 현재 모드뿐 아니라 증가하는 version과 변경 시각을 함께 둡니다. 저장이 성공한 뒤에만 Broadcast 이벤트를 보냅니다. 이벤트는 성공했지만 상태 저장은 실패하는 순서를 피하기 위해서입니다.

Redis가 절대적인 정답이라는 뜻은 아닙니다. 트랜잭션과 영속성이 더 중요한 서비스라면 Postgres가 원본이 될 수 있습니다. 핵심은 모든 클라이언트가 다시 물어볼 수 있는 권위 있는 현재 상태가 하나 존재한다는 점입니다.

상태 변경 명령은 같은 요청이 두 번 도착해도 안전하도록 만듭니다. 이벤트 ID나 목표 version을 사용하면 네트워크 재시도로 같은 명령이 중복되어도 이미 처리한 상태를 다시 망가뜨리지 않습니다. 유실을 복구하려고 재시도를 넣는 순간 중복 처리도 함께 설계해야 합니다.

2. Broadcast는 전체 상태가 아니라 신호를 보낸다

Broadcast에는 전체 상태보다 “상태가 version 42로 변경됐다”는 작은 신호를 담습니다. 클라이언트는 자신이 알고 있는 version과 비교합니다. 바로 다음 version이라면 최소 정보로 화면을 갱신하고, 중간 version을 건너뛰었다면 원본 상태를 다시 조회합니다.

동일한 이벤트가 두 번 도착해도 이미 처리한 version이면 무시할 수 있습니다. 늦게 도착한 과거 이벤트도 버릴 수 있습니다. 반대로 현재보다 두 단계 이상 앞선 이벤트가 오면 메시지를 놓쳤다고 판단해 전체 동기화를 실행합니다.

바이너리는 여기서 선택적으로 사용합니다. 화면 전환처럼 작은 제어 신호는 JSON이 디버깅에 편합니다. 좌표, 타이머 tick, 다량의 수치나 축소 이미지 프레임을 반복한다면 바이너리가 의미를 가집니다. 형식이 달라져도 type, version, sequence라는 의미 계약은 유지해야 합니다.

3. 재연결하면 전체 상태를 다시 맞춘다

WebSocket이 다시 연결됐다는 사실만으로 동기화가 끝난 것은 아닙니다. 끊어진 동안 어떤 이벤트를 놓쳤는지 확인해야 합니다. 클라이언트가 채널에 재구독하거나 백그라운드에서 돌아오면 원본 상태를 한 번 읽고 자신의 version과 비교합니다.

구독과 snapshot 조회 사이의 race condition도 고려해야 합니다. 먼저 snapshot을 읽고 나중에 구독하면 그 짧은 사이의 이벤트를 놓칠 수 있습니다. 실용적인 방법은 채널을 먼저 구독한 뒤 snapshot을 읽고, 그동안 도착한 이벤트를 version 기준으로 정리하는 것입니다. 어느 순서를 택하든 마지막에는 원본과 클라이언트의 version이 같은지 확인해야 합니다.

4. 연결이 실패하면 jitter가 있는 polling으로 내려간다

재연결이 바로 되지 않을 때는 polling을 안전망으로 사용했습니다. 연결 실패 상태의 클라이언트는 짧은 간격으로 상태를 조회하되, 모든 기기가 정확히 같은 시점에 요청하지 않도록 작은 무작위 지연, 즉 jitter를 더합니다. WebSocket이 회복되면 polling을 중단하거나 훨씬 느린 상태 확인으로 바꿉니다.

jitter가 없으면 네트워크가 복구된 순간 모든 기기가 동시에 서버를 두드리는 thundering herd가 생길 수 있습니다. 장애가 오래 지속되면 간격을 점차 늘리는 backoff도 필요합니다. 특정한 polling 주기보다 중요한 원칙은 실시간 채널이 실패해도 상태를 확인할 두 번째 경로가 있다는 것입니다.

Broadcast Replay가 있으니 polling은 없어도 될까?

Supabase에는 연결이 끊긴 동안의 일부 메시지를 다시 가져오는 Broadcast Replay도 있습니다. 다만 2026년 8월 공식 문서상 private channel에서 Database가 보낸 Broadcast만 replay 대상입니다. 클라이언트끼리 직접 보낸 모든 메시지를 자동 보관하는 범용 event log가 아닙니다.

기본 보관 한도는 72시간이고 한 요청에서 가져올 수 있는 메시지는 최대 25개입니다. 메시지는 일별 partition에 저장되어 실제로는 최대 약 4일 남을 수 있지만, 애플리케이션이 그 추가 시간을 보장처럼 사용해서는 안 됩니다.

Replay는 짧은 연결 중단 뒤 최근 맥락을 복원하는 데 유용하지만 전체 상태 저장소를 대체하지 않습니다. 이벤트가 25개보다 많거나 보관 기간을 지났거나 client Broadcast를 썼다면 replay만으로 현재 상태를 재구성할 수 없습니다. Redis나 Postgres의 snapshot을 다시 읽는 경로가 여전히 필요합니다.

Supabase도 공식 기술 글에서 Realtime은 live UI를 위한 best-effort 전달이고, 연결이 끊긴 동안의 변경을 일반적인 queue처럼 재전송하지 않는다고 구분합니다. 내구성 있는 분석 데이터 이동에는 at-least-once 전달을 지향하는 Pipelines 같은 별도 도구가 필요합니다. 둘은 경쟁 기능이 아니라 목적이 다른 기능입니다.

바이너리 도입 전 체크리스트

  • 작고 낮은 빈도의 명령은 JSON이 더 단순하지 않은가?
  • 모든 활성 클라이언트 SDK가 바이너리를 지원하는가?
  • 기능 플래그와 JSON fallback으로 점진 배포할 수 있는가?
  • 메시지 종류, protocol version, sequence, byte order를 문서화했는가?
  • 바이너리를 암호화로 착각하지 않고 인증과 권한을 별도로 적용했는가?
  • payload 크기뿐 아니라 초당 메시지와 수신자 fan-out을 계산했는가?
  • Redis나 데이터베이스에 현재 상태와 version이 남는가?
  • 같은 이벤트가 중복되거나 순서가 바뀌어도 안전한가?
  • 재연결 직후 full-state sync를 수행하는가?
  • jitter와 backoff가 있는 fallback이 있는가?
  • 네트워크 전환, 화면 잠금, 구버전 클라이언트와 메시지 유실을 시험했는가?

좋은 실시간 시스템은 메시지를 놓쳐도 회복한다

Supabase Realtime의 바이너리 지원은 의미 있는 업데이트입니다. JSON과 잘 맞지 않던 센서, 이미지 프레임, 고빈도 수치를 같은 Broadcast 인프라에서 더 자연스럽게 처리할 수 있게 됐습니다.

하지만 payload가 바뀌어도 네트워크 단절, 메시지 순서, 재연결 공백은 사라지지 않습니다. 제가 택한 답은 Redis는 현재 상태의 원본, Broadcast는 빠른 신호, 재연결 시 전체 상태 동기화, WebSocket 장애 시 jitter가 있는 polling이었습니다. 바이너리는 이 구조의 속도를 개선할 수 있지만 구조 자체를 대신하지는 않습니다.

실시간 시스템의 품질은 모든 메시지가 완벽하게 도착하는 순간보다, 메시지 몇 개가 사라진 뒤에도 모든 사용자가 결국 같은 상태로 돌아오는 순간에 드러납니다.
